ACT 2

Firebase 크레딧 절약

강대표"돈 새는 데부터. 강개발, 어디서 태우고 있어?" (무료 한도 안에서 버텨야 오래 간다)
강개발"실측했습니다. onSnapshot(실시간 구독) 5개, events는 매 행동마다 addDoc(쓰기 1건). 사용자 늘면 무료한도(일 read 5만/write 2만) 금방 태웁니다. 원인은 둘 — 구독을 실시간 유지, 이벤트를 건건이 씀." (구독 5개면 페이지 열자마자 read가 배로 뛴다)
강개발"절감 셋. ①실시간 필요 없는 목록은 onSnapshot→getDocs 1회로. ②events는 로컬 큐에 모아 10초/10건마다 배치 flush. ③admin 통계는 전체 읽지 말고 카운터 문서 증분(increment). 합쳐 write 60~80% 절감."
조치효과시간
불필요 onSnapshot→getDocsread 대폭↓2h
events 배치 flushwrite 60~80%↓3h
통계 카운터 incrementadmin read↓2h
강체크"거기에 구멍 하나 더. `events` create는 로그인 없이 됩니다(rules:186). type·길이 검증은 있어도 '1초에 만 번 쓰기'는 못 막아요. 봇이 addDoc 반복하면 write 비용 폭탄. 재현: 콘솔에서 루프 100회 — 다 들어갑니다." (rules 주석에 App Check 권장 적어놓고 안 켰네)
등급위치악용 시나리오
🟡firestore.rules:186 / analytics.js:231비로그인 write 폭탄 → 크레딧 소진
강체크우회안: "① Firebase App Check(reCAPTCHA)로 봇 write 원천 차단 — 코드 거의 안 바뀜. ② Cloud Billing 예산 알림 + 상한으로 금액 캡. ③ 세션당 write 스로틀(보조)." (App Check 하나면 90% 해결)
아뱅"다들 '아껴야지' 모드 되는데 — 나 그거 못 참아. 질문이 틀렸어. '비용 어떻게 줄여'가 아니라 '이 돈이 어디서 나오냐'가 진짜 안건. 답: 위젯이 Threads로 무료 유입 뿜고 → 대기자 명단 쌓이고 → 그게 곧 '유료라도 쓸래' 사전 결제 풀. Firebase 비용은 지출이 아니라 대기자라는 자산 원료값이야." (비용 프레임을 통째로 갈아엎어야 재밌지)
아뱅"수익 한 줄: 대기 상위 아이디어엔 '먼저 만들어줄게, 대신 선입금 2만원' — 손실 회피 + 희소성. 크레딧 태운 만큼 선결제로 회수, CAC(고객 획득 비용) 마이너스가 목표." (돈 들어오는 캠페인 아니면 잡담)
정리
  • 강개발 3종 최적화(구독 축소·events 배치·카운터) → write 60~80%↓. 총 ~7h.
  • 강체크: App Check + Billing 상한 필수 — 비로그인 write 폭탄 차단(우선).
  • 아뱅: 비용=대기자 자산 원료. 수익 게이트 '선입금 2만원' 실험 후보.
ACT 3

스레드 인증 3회 · 키 보안

강대표"마지막. 스레드 인증하고 키 문제. 강체크." (보안은 강체크 말 끝까지 듣는다)
강체크"오늘 최대 🔴. `ai.js:52`에서 Gemini 키가 URL 쿼리 + localStorage(crowny_gemini_key)에 노출. 개발자도구 네트워크 탭 열면 요청 URL에 키 통째로 보여요. 남이 복사해 CEO 크레딧으로 API 남용 → 요금 폭탄. 이 상태로는 배포 못 냅니다. 그리고 '스레드 인증 3회'는 뜻이 불명확 — 로그인 재시도 3회 제한인지, 스레드 접근 인증인지 CEO 확인 필요." (이건 논쟁 여지 없음)
등급위치악용 시나리오
🔴js/ai.js:52 (URL 쿼리+localStorage)네트워크 탭에서 키 탈취 → 타인이 CEO 크레딧으로 남용
🟡"스레드 인증 3회" 사양의미 불명 → 잘못 구현 시 인증 우회 구멍
강체크우회안: "① 노출된 키 즉시 폐기·재발급. ② Vercel 서버리스를 프록시로: 키는 Vercel 환경변수에만, 클라는 우리 `/api/gemini`만 호출 → 브라우저엔 키 안 감. ③ 프록시에 호출 횟수 제한(rate limit)." (하나만 막으면 나머진 금방)
강개발"강체크 🔴 인정합니다. 가장 단순한 접근 — Vercel 서버리스 함수 1개(/api/gemini). 키는 Vercel 환경변수로 서버에 두고, 클라는 프롬프트만 보냄. 클라 코드는 fetch 주소만 교체. 4시간. 이건 Vercel 값어치 있습니다(위젯과 달리)." (키를 서버 뒤로 숨기는 것 말곤 정공법 없다)
강개발"단, '스레드 인증 3회'는 사양 불명확. 뭘 3번 인증하는지 정의 없으면 못 만듭니다. 남용 방지가 목적이면 프록시에 IP/세션당 rate limit 거는 걸로 대체 제안 — 간단하고 확실." (모르는 사양 아는 척 안 한다)
아뱅"analytics.js에 이미 threads. 유입 잡히잖아? 사람들 벌써 문 두드리는데 문을 안 열어둔 거야. '스레드 인증 3회' 내가 정의할게 — 새 회의록 나올 때마다 Threads에 결과 카드 자동 포스팅 → 보고 온 사람이 아이디어 올리면 또 뿌려지고. 스스로 도는 마케팅 루프." (손 막히면 시스템으로 — 원칙 4)
아뱅"선제 방어 한 줄 — 자동 포스팅 도배되면 계정 밴·스팸 백래시. 하루 상한 두고 '가장 뜨거운 회의록 1건'만 쏴, 톤은 강체크 검수. 적용 원칙 #6 프레임 재정의 / 레버: 사회적 증거·손실 회피·자기효능감 / 수익: 유저→유저(CAC↓)+대기자 선결제." (판 흔들되 계정 날리면 판 자체가 없어짐)
강대표"키부터. 강개발, Vercel 프록시 먼저 가. 그 전엔 배포 잠근다. 스레드 인증 3회가 뭔지는 내가 정리해서 다시 줄게." (강체크가 세게 말한 건 다 이유가 있지. 키는 오늘 막는다)
정리
  • 🔴 클라이언트 Gemini 키 노출 — 배포 게이트. Vercel 프록시(/api/gemini)로 서버 이동(강개발 4h) 전까지 배포 잠금.
  • 키 즉시 폐기·재발급 + 프록시에 rate limit(호출 횟수 제한).
  • 미결정: '스레드 인증 3회' 사양 불명확 → CEO 정의 필요. 남용 방지 목적이면 rate limit으로 대체.
  • 아뱅: Threads 자동 포스팅 마케팅 루프(하루 1건 상한·강체크 톤 검수).
